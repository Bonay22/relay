## Завершённый инкремент: happy path `NewEvent`

`event_test.go` проверяет успешный `NewEvent`: отсутствие ошибки, тип, начальный
статус, наличие и значение `order_id`, а также ненулевой `CreatedAt`.

Подтверждены устройство `*_test.go`, роль `*testing.T`, различие
`Fatalf`/`Errorf`, логика Arrange — Act — Assert и comma-ok. В текущем тесте map
literal и вызов конструктора объединяют Arrange и Act в одной инструкции, а
чтение результата через comma-ok относится к Assert.

## Завершённый инкремент: sentinel-ошибка пустого типа

`ErrEventTypeEmpty` объявлена один раз на уровне пакета и возвращается из
`NewEvent`. Отдельный тест использует `errors.Is`, а zero value результата
проверяет по полям, поскольку `Event` содержит несравнимую map.

Подтверждены отличие общей ошибки от нового `errors.New` с тем же текстом,
поведение `errors.Is(nil, target)` и проверка `Type`, `Status`, `Payload` и
`CreatedAt` на ошибочном пути.

## Завершённый инкремент: table-driven happy paths

`TestNewEvent` преобразован в таблицу из трёх случаев: `order_created`,
`order_paid` и `nil_payload`. Общий subtest проверяет тип, статус, время и
payload; nil payload зафиксирован как допустимый вход.

Подтверждены тип slice `[]struct { ... }`, тип одного элемента
`struct { ... }`, отличие типа от значения, работа `range`, blank identifier,
function literal и граница `return`/`Fatalf` внутри subtest.

## Завершённый инкремент: `MarkDelivered` и red-green

Для nil receiver добавлена sentinel-ошибка `ErrEventNil`. Успешная смена
`EventPending` на `EventDelivered` и ошибочный nil-путь защищены отдельными
тестами. Повторяющаяся проверка неожиданной ошибки вынесена в
`requireNoError`, а `t.Helper()` направляет диагностику на строку вызова.

Проверка red-green выполнена: временная замена `EventDelivered` на
`EventPending` вызвала ожидаемое падение focused test; после восстановления
production-кода полный набор тестов снова прошёл.

## Необходимые объяснения и примеры

Helper — обычная функция тестового файла. Вызов `t.Helper()` помечает её как
вспомогательную, чтобы диагностика указывала на строку вызова helper, а не на
его внутренний `t.Fatalf`. Выделяется только реально повторяющаяся проверка
неожиданной ненулевой ошибки.

Nil pointer `var event *Event` можно использовать как receiver метода с
pointer receiver. Метод обязан проверить receiver до разыменования и вернуть
семантическую ошибку. Для неё используется отдельный sentinel `ErrEventNil`.

Red-green — практическая проверка полезности теста: сначала тесты проходят,
затем временная поломка ожидаемого поведения вызывает падение, после
восстановления production-кода тесты снова проходят.

## Реализованный сценарий

- созданное событие начинается со статуса `EventPending`;
- `MarkDelivered` возвращает `nil` и изменяет оригинал на `EventDelivered`;
- вызов метода через nil receiver возвращает ошибку, распознаваемую через
  `errors.Is(err, ErrEventNil)`, и не вызывает panic;
- helper применяется только к повторяющейся проверке неожиданной ошибки;
- намеренная регрессия обнаруживается focused test, а после восстановления весь
  набор снова становится зелёным.

## Решения и ход реализации

- Тест находится рядом с `event.go` и использует тот же пакет `main`, потому что
  доменная модель пока не выделена в импортируемый пакет.
- Первый тест намеренно защищает только один успешный сценарий.
- Тестовый runner не вызывает обычную `func main()`; он запускает найденные
  функции `TestXxx` через собственную точку входа.
- Причина пустого типа представлена общей `ErrEventTypeEmpty`; тесты не зависят
  от текста сообщения.
- Успешные варианты конструктора образуют три именованных subtest; nil payload
  явно допустим.
- Nil receiver метода `MarkDelivered` считается ошибкой вызывающего кода и
  возвращает общую `ErrEventNil`.
- `requireNoError` оставлен узким helper для случаев, где дальнейшие проверки
  бессмысленны после неожиданной ошибки.
- Red-green эксперимент подтвердил, что тест смены статуса действительно
  обнаруживает регрессию.
